# Security model

This document states what ShieldForge protects, how, and — just as importantly — what it
does **not** protect yet.

## What this build does not do

* It does not detect malware. No engine is configured.
* It does not provide real-time / on-access protection on any platform.
* It does not disable, bypass or weaken Microsoft Defender, Windows Security, Gatekeeper,
  or any other platform control. There is no code path that touches them.
* It does not upload files, hashes or telemetry. There is no such backend.
* It does not run as a privileged service, and Phase 1 deliberately avoids creating one.

## Trust boundaries

1. **Webview → Rust.** The webview is treated as untrusted input. Every value it sends is
   re-validated in Rust (`shieldforge_core::validation`) even though the UI already
   validated it.
2. **Rust → engine.** Engines run as child processes with an **argument vector** — never
   through a shell — with bounded output (8 MB) and a hard timeout.
3. **Rust → filesystem.** Only two locations are writable: the application data directory
   (logs, vault) and, for a restore, the recorded original path of the item.

## Command surface (least privilege)

The webview can reach exactly 14 commands, all defined in `src-tauri/src/commands.rs` and
enumerated in `src-tauri/capabilities/default.json`:

```
get_app_info   get_protection_status   get_scanner_descriptor
scan_start     scan_progress           scan_cancel   scan_results
quarantine_list  quarantine_restore    quarantine_delete
update_status  update_check            history_list  audit_list
```

Not granted: any filesystem plugin permission, shell/process execution, HTTP client,
dialog, notification or store plugin permission. The CSP in `tauri.conf.json` restricts
the webview to `self` plus the Tauri IPC endpoint. `withGlobalTauri` is disabled so the
page has no global Tauri object.

> Note: `capabilities/default.json` uses the `allow-<command>` permission identifiers that
> Tauri 2 generates for application commands. Verify the generated names against
> `src-tauri/gen/schemas/` after the first `tauri build` on a machine with the Rust
> toolchain; adjust the list if the ACL schema differs in your Tauri 2.x patch release.

## Input validation

Authoritative rules live in `shieldforge_core::validation`; `src/lib/validation.ts` mirrors
them for immediate feedback.

| Input | Rule |
|---|---|
| Custom scan target | Absolute (`C:\…`, `D:/…`, `/…`), no `..`, no NUL, no `< > : " \| ? *` or control characters (the drive colon is allowed), ≤ 32 767 chars |
| Scan profile | `quick` \| `full` \| `custom` only |
| Job id | `job_[A-Za-z0-9_-]{4,64}` |
| Quarantine id | `qtn_[A-Za-z0-9_-]{4,}`, ≤ 128 chars |
| Numeric preferences | Clamped into documented ranges (1–4096 MB, 1–720 min, 1–365 days, 5–200 rows) |

## Quarantine safety

* A file is isolated **only** for a detection reported by a configured engine. The UI has
  no way to request isolation for a path it merely dislikes.
* Vault entry ids are generated by the service and validated against the grammar before
  they are joined onto the vault path, so `../../etc/passwd` cannot escape.
* `restore` writes back to the recorded original path and **refuses to overwrite** an
  existing file.
* `delete` is permanent; the UI requires the user to type `DELETE` before it is enabled.
* If metadata cannot be written after the file has been moved, the move is rolled back so
  the vault never claims an item it cannot restore.
* Every action appends an audit record (success **and** failure).

## Update security

`shieldforge_core::updates` implements the policy; nothing is trusted by default.

* An update package is accepted only after **signature verification** against a trust
  store. `UnconfiguredTrustStore` (the Phase 1 default) rejects everything.
* Unsigned, malformed, empty or unversioned packages are rejected with a recorded reason —
  never “trusted anyway”.
* `UpdateStatus.signatures_verified` is `true` only for a verified package, and the UI
  shows `Not verified` otherwise.
* Hosts are expected to be pinned and TLS-validated when a real source is configured.

Future work: an offline ed25519 signing key, a pinned mirror, rollback metadata and a
staged rollout. None of that exists yet.

## Audit logging

`FileAuditLog` appends JSON lines to the application data directory and compacts to a
bounded retention window (500 records by default). Malformed lines are counted and
skipped, never reinterpreted. The log is an operational record, **not tamper-proof** —
the UI says so. A hardened log (hash chaining, OS-level protection) is future work.

## Process execution (ClamAV adapter)

* `Command::new(binary).args([...])` — no shell, therefore no command injection.
* stdin closed, stdout/stderr piped, output capped at 8 MB, hard wall-clock timeout with
  `child.kill()` on expiry.
* Exit code 0 (clean) and 1 (something found) both succeed; anything else is an error.
* Output parsing (`parse_clamscan_output`) is a pure function with tests for well-formed,
  malformed and hostile input. Unparseable lines are ignored — never counted as clean.

Licensing: ClamAV is **GPL-2.0-only**. Redistributing its binaries or signature databases
carries obligations that must be reviewed before shipping; this adapter talks to a
user-installed binary and is disabled by default.

## Known gaps

* No integrity protection on the audit log (see above).
* No code signing for the Windows installer in this repository (configure
  `bundle.windows.certificateThumbprint` and a timestamp URL before release).
* No anti-tamper or self-protection of the application directory.
* No privileged service: none is needed for on-demand scanning, and adding one would
  enlarge the attack surface.
* The Rust layer in this checkout has **not been compiled or tested** (no toolchain in the
  authoring sandbox). Run `npm run test:rust` before relying on it.
